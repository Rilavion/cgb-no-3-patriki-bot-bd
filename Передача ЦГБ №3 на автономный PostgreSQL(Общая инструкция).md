# Передача ЦГБ №3 на автономный PostgreSQL

Документ предназначен владельцу новой базы и администратору сайта. Итоговая архитектура полностью исключает Supabase из рабочей системы.

## 1. Итоговая архитектура

```text
Пользователь → HTTPS/Nginx → статический сайт
                         ↘ /api/v1 → CGB API → PostgreSQL
                                      ↘ /media → файлы на VPS

Discord-бот ─────────────────────────────────→ PostgreSQL
Telegram-воркер ─────────────────────────────→ PostgreSQL
```

- Браузер не подключается к PostgreSQL и не получает пароль базы.
- Собственный Node.js API выполняет авторизацию, проверку ролей, запросы сайта и загрузку файлов.
- Discord-бот подключается напрямую отдельным пользователем и получает события через `LISTEN/NOTIFY`.
- Telegram-воркер читает очередь напрямую из PostgreSQL.
- Фото состава и автопарка хранятся на VPS в `/var/lib/cgb-storage`, а не в БД.

## 2. Что должен предоставить владелец PostgreSQL

PostgreSQL 15 или новее и следующие данные:

- хост, порт и имя базы;
- отдельные логины и пароли для API сайта, Discord-бота и Telegram-воркера;
- обязательный TLS: режим `require` либо корневой сертификат CA;
- разрешение подключений с IP VPS сайта `62.109.27.123`;
- разрешение с будущего хоста Discord-бота и Telegram-воркера;
- временный пользователь-владелец для применения схемы и импорта.

Рекомендуемый минимум: 1 vCPU, 1 ГБ RAM, 10 ГБ SSD, ежедневные резервные копии минимум за 7 дней. Часовой пояс самой БД лучше оставить UTC.

## 3. Создание базы и пользователей

Пример выполняется администратором PostgreSQL. Пароли заменить и не отправлять в открытом сообщении:

```sql
create role cgb_owner login password 'OWNER_PASSWORD';
create database cgb owner cgb_owner encoding 'UTF8';

-- После применения 02-runtime-grants.sql:
create role cgb_api login password 'API_PASSWORD' in role cgb_api_role;
create role cgb_bot login password 'BOT_PASSWORD' in role cgb_bot_role;
create role cgb_telegram login password 'TELEGRAM_PASSWORD' in role cgb_telegram_role;
```

Если хостинг не разрешает создавать роли, допустим один выданный пользователь-владелец для первого запуска. Разделение прав желательно выполнить сразу после переноса.

## 4. Подготовленные файлы

- `01-schema.sql` — таблицы, функции, триггеры, собственная авторизация и события БД;
- `02-runtime-grants.sql` — групповые права сервисов;
- `export-supabase.mjs` — одноразовая выгрузка старых данных и Storage;
- `import-postgres.mjs` — импорт в новую БД и копирование файлов;
- `verify-postgres.mjs` — сверка количества записей и функций;
- `set-user-password.mjs` — назначение нового пароля пользователю;
- `.env.example` — образец переменных без секретов.

## 5. Важный выбор по старым паролям

Служебный ключ Supabase позволяет выгрузить пользователей, но не их хеши паролей.

Есть два варианта:

1. Получить в Supabase строку прямого подключения к базе (`SUPABASE_DATABASE_URL`). Тогда экспортёр переносит bcrypt-хеши, и старые пароли продолжают работать.
2. Не предоставлять прямое подключение. Пользователи переносятся с флагом обязательной смены пароля; администратор назначает им новые пароли командой из раздела 9.

Служебный ключ и строки подключения нужны только на время миграции. Они не входят в сайт, бота, GitHub или итоговый серверный пакет.

## 6. Пробный экспорт и импорт

На защищённом компьютере с Node.js 20+:

```bash
cd postgres-migration
npm ci
cp .env.example .env
```

Заполнить `.env`, затем:

```bash
npm run export
npm run import
npm run verify
```

`export/manifest.json` содержит контрольные количества и SHA-256 выгруженных таблиц. Каталог `export/` содержит персональные данные и никогда не загружается в GitHub.

При импорте старые постоянные ссылки вида `.../storage/v1/object/public/...` автоматически заменяются на локальные `/media/...`; сами объекты копируются в `STORAGE_ROOT`. Поэтому после отключения Supabase фото состава и автопарка продолжат открываться с VPS.

Если схема применяется владельцем отдельно:

```bash
psql "$OWNER_DATABASE_URL" -v ON_ERROR_STOP=1 -f 01-schema.sql
psql "$OWNER_DATABASE_URL" -v ON_ERROR_STOP=1 -f 02-runtime-grants.sql
```

После этого для импортёра можно задать `APPLY_SCHEMA=false`.

## 7. Установка API сайта

На VPS сайта:

```bash
sudo useradd --system --home /opt/cgb-postgres-api --shell /usr/sbin/nologin cgb-api
sudo mkdir -p /opt/cgb-postgres-api /var/lib/cgb-storage
sudo cp -a server/postgres-api/. /opt/cgb-postgres-api/
cd /opt/cgb-postgres-api
sudo npm ci --omit=dev
sudo cp .env.example /etc/cgb-postgres-api.env
sudo chmod 600 /etc/cgb-postgres-api.env
sudo chown -R cgb-api:cgb-api /opt/cgb-postgres-api
sudo chown -R cgb-api:www-data /var/lib/cgb-storage
sudo chmod 750 /var/lib/cgb-storage
```

В `/etc/cgb-postgres-api.env` заполнить:

```dotenv
DATABASE_URL=postgresql://cgb_api:PASSWORD@DB_HOST:5432/cgb
PGSSL=require
JWT_SECRET=СЛУЧАЙНАЯ_СТРОКА_НЕ_КОРОЧЕ_48_СИМВОЛОВ
JWT_TTL=8h
REFRESH_DAYS=30
PUBLIC_ORIGIN=https://cgb3patriki.ru,https://www.cgb3patriki.ru
STORAGE_ROOT=/var/lib/cgb-storage
PORT=8787
TRUST_PROXY=true
```

Установить `cgb-postgres-api.service`, включить службу и применить подготовленный Nginx-конфиг `server/cgb3-domain.conf`. API слушает только `127.0.0.1:8787`.

Проверка:

```bash
curl https://cgb3patriki.ru/api/v1/health
```

## 8. Discord-бот и Telegram

Discord-бот подготовлен в передаваемой папке. В его `.env` задаются `DATABASE_URL` пользователя `cgb_bot`, `PGSSL=require` и Discord-переменные. Выполнить `npm ci --omit=dev`, затем запустить systemd-службу по `POSTGRESQL-BOT-SETUP.md`.

Telegram-воркер находится в `telegram-bot/`. Использовать пользователя `cgb_telegram`; инструкция находится в `TELEGRAM-BOT-SETUP.md`. Если с хоста заблокирован `api.telegram.org`, дополнительно задать `OUTBOUND_PROXY_URL`.

## 9. Назначение новых паролей

Если хеши не переносились:

```bash
npm run set-password -- user@example.org 'Новый-надёжный-пароль'
```

Команда обновляет bcrypt-хеш в новой базе и снимает флаг обязательного сброса. Пароль не следует оставлять в истории терминала; для постоянной эксплуатации лучше вызывать скрипт в защищённой административной сессии.

## 10. Финальное переключение без потери данных

1. За 15–30 минут предупредить пользователей и временно закрыть создание/редактирование заявок.
2. Остановить старые Discord- и Telegram-процессы, чтобы они не меняли источник.
3. Сделать финальный экспорт Supabase.
4. Импортировать его в очищенную целевую БД или повторно выполнить idempotent-импорт.
5. Выполнить `npm run verify`; отдельно сравнить пользователей и число файлов.
6. Скопировать сайт, включить API и Nginx.
7. Запустить Discord-бот и Telegram-воркер с новыми строками подключения.
8. Проверить вход администратора, роли, новости, состав/фото, создание тестовой заявки, вердикт и оба уведомителя.
9. Открыть сайт пользователям.

Нельзя одновременно оставлять старых и новых обработчиков очередей: возможны дубли уведомлений.

## 11. Откат

До подтверждения проверки не удалять старый проект. При критической ошибке:

1. закрыть сайт на обслуживание;
2. остановить новые API/боты;
3. вернуть предыдущие файлы сайта и старые процессы;
4. восстановить данные из последней резервной копии или повторить экспорт после исправления.

После успешной эксплуатации новой системы несколько дней выгрузку следует зашифровать и сохранить как аварийную копию, затем безопасно удалить с рабочего компьютера.

## 12. Полный отказ от Supabase после приёмки

- убедиться, что HTML загружает `database-loader.js` и `database-config.js`, а не старый клиент;
- удалить с VPS неиспользуемые `supabase.js`, `supabase-loader.js`, старый `config.js` и старый PHP-маршрут удаления пользователя;
- остановить старые relay/cron/edge-функции;
- отозвать/заменить ранее раскрытые ключи;
- скачать последнюю резервную копию;
- только после приёмки удалить или приостановить проект Supabase.
