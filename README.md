# ЦГБ №3 — техническое описание проекта

Веб-портал Центральной городской больницы №3 для игрового проекта RMRP. Система объединяет публичный сайт, рабочий кабинет сотрудников, формы заявлений, внутренние проверки, тестирование, документы, состав организации, Discord-бота и Telegram-уведомления.

- Рабочий сайт: [https://cgb3patriki.ru](https://cgb3patriki.ru)
- Репозиторий Discord-бота: [github.com/Rilavion/cgb-no-3-patriki-bot](https://github.com/Rilavion/cgb-no-3-patriki-bot)
- Основной язык интерфейса: русский
- Часовой пояс проекта: `Asia/Irkutsk`

## 1. Фактическое состояние версии в репозитории

Репозиторий содержит снимок `/var/www/html` рабочего VPS от 19 августа 2026 года:

- 193 файла общим объёмом около 19 МБ;
- 46 рабочих HTML-страниц;
- 46 JavaScript-файлов;
- 2 CSS-файла, включая общий `style.css`;
- изображения интерфейса, устава, состава и автопарка;
- серверные копии отдельных файлов с суффиксом `.bak-*`.

Эта версия является фактически опубликованной версией сайта. На момент выгрузки она работает через Supabase:

- `config.js` содержит публичную конфигурацию клиентского подключения;
- `supabase-loader.js` загружает локальную сборку `supabase.js`;
- Supabase Auth выполняет вход по email и паролю;
- PostgREST обслуживает обращения к таблицам и RPC;
- Realtime используется для части живых обновлений;
- Storage используется для фотографий состава и автопарка.

Параллельно подготовлена целевая версия для полного перехода на автономный PostgreSQL. Она включает собственный API, собственную авторизацию, отдельные подключения ботов и хранение загруженных изображений на VPS. До финальной миграции рабочий снимок и подготовленную PostgreSQL-версию необходимо различать: файлы в этом каталоге отражают текущее состояние VPS, а не уже выполненное переключение.

## 2. Назначение компонентов

| Компонент | Назначение | Технологии |
|---|---|---|
| Публичный сайт | Информация, услуги, медикаменты, новости, состав, автопарк, карта, FAQ, устав | HTML5, CSS3, JavaScript |
| Внутренний интерфейс | Авторизация, заявки, жалобы, тесты, отчёты, настройки и статистика | JavaScript, Supabase SDK в текущей версии |
| API PostgreSQL-версии | Авторизация, проверка ролей, работа с таблицами/RPC, приём изображений | Node.js 20, Express, `pg` |
| Discord-бот | Получение событий сайта, публикация Embed, синхронизация каналов, ролей и участников | Node.js, discord.js |
| Telegram-воркер | Получение очереди уведомлений и отправка по темам Telegram-группы | Python 3.11+, psycopg |
| Текущая база | Данные сайта, Auth, Storage и Realtime | Supabase/PostgreSQL |
| Целевая база | Все прикладные таблицы, функции, события и пользователи сайта | PostgreSQL 15+ |
| Экспорт PNG | Состав, статистика и медицинские услуги без серверной генерации | html2canvas, Canvas API |

Сайт не использует frontend-фреймворк и не требует сборки Webpack/Vite. Каждая страница подключает общий набор JavaScript-модулей и свой модуль раздела.

## 3. Схема работы текущей версии

```text
Браузер
  ├── HTML/CSS/JS с VPS
  ├── Supabase Auth — вход и сессия
  ├── PostgREST — таблицы и RPC
  ├── Realtime — часть событий
  └── Storage — фото состава и автопарка

Discord-бот
  ├── Discord Gateway
  ├── таблицы сайта
  ├── очереди запросов
  └── синхронизация Discord → БД

Telegram-воркер
  ├── таблица очереди telegram_notifications
  ├── настройки маршрутов
  └── Telegram Bot API
```

Схема после финального перехода:

```text
Браузер
  │ HTTPS
  ▼
Nginx
  ├── /                → статические файлы сайта
  ├── /api/v1/*        → Node.js API на 127.0.0.1:8787
  └── /media/*         → изображения в /var/lib/cgb-storage
                              │
                              ▼
                         PostgreSQL 15+
                           ├── cgb_api
                           ├── cgb_bot      → Discord
                           └── cgb_telegram → Telegram
```

Discord-бот и Telegram-воркер не соединяются друг с другом. Каждый процесс самостоятельно подключается к одной базе данных с собственным пользователем и получает только предназначенные ему данные.

## 4. Загрузка страницы и общие JavaScript-модули

Типовая внутренняя страница загружает скрипты в следующей последовательности:

1. `supabase-loader.js` — создаёт доступ к Supabase SDK.
2. `config.js` — задаёт URL проекта и публичный клиентский ключ.
3. `auth.js` — восстанавливает сессию, выполняет вход/выход и проверяет наличие пользователя в `user_roles`.
4. `roles-engine.js` — загружает роль, пользовательские разрешения и применяет ограничения элементов интерфейса.
5. `main.js` — навигация, фон, переходы, общие кнопки и поведение интерфейса.
6. Модули оформления: `holiday-engine.js`, `settings-panel.js`, `sound-engine.js`.
7. Служебные модули: `search-engine.js`, `ds-cache.js`, `notify-engine.js`, `notify-live.js`.
8. Модуль конкретной страницы: например, `requests-engine.js`, `tests-engine.js` или `composition-engine.js`.

Модули публикуют общий API через `window.CGB_*`. Например:

- `window.CGB_AUTH` — состояние клиента, пользователь и операции входа;
- `window.CGB_ROLES` — роль, разрешения и назначение роли;
- `window.CGB_NEWS` — чтение новостей и справочники тегов;
- `window.CGB_COMPOSITION` — чтение/сохранение состава и загрузка фото;
- `window.CGB_REQUESTS` — формы заявок и изменение статусов;
- `window.CGB_TESTS` — тесты, вопросы, попытки и вердикты.

## 5. Авторизация и модель доступа

### Текущая реализация

`auth.js` создаёт Supabase-клиент и вызывает `auth.getSession()`. После получения пользователя дополнительно проверяется запись в `user_roles`. Если запись удалена, локальная сессия отклоняется и выполняется выход. Поэтому существование аккаунта в Auth само по себе не даёт доступ к внутренним страницам.

Вход выполняется через `signInWithPassword`. Сессия восстанавливается Supabase SDK и отслеживается через `onAuthStateChange`.

### Роли

Основные данные роли находятся в:

- `user_roles` — связь пользователя с ролью, отображаемое имя и `custom_role_id`;
- `custom_roles` — название роли, цвет, описание, базовая роль и JSON с разрешениями.

`roles-engine.js` загружает обе записи и проверяет доступ методом `CGB_ROLES.can(section, action)`. Элементы HTML ограничиваются атрибутом:

```html
data-perm="requests:review"
```

Можно перечислить несколько разрешений через запятую. Достаточно любого из них.

Базовые классы состояния на `<body>`:

- `cgb-is-logged` — пользователь авторизован;
- `cgb-is-admin` — базовая роль `admin`;
- `cgb-is-ss` — базовая роль `ss`;
- `cgb-is-staff` — администрация или старший состав.

Роль `admin` получает полный доступ на уровне клиентского движка. Остальные роли используют JSON-разрешения из `custom_roles`. Для роли `ab_operator` отдельно сохранена совместимость с подачей запросов АБ.

### Разделы разрешений

Справочник `roles.html` отображает разрешения по следующим группам:

- заявления;
- жалобы;
- реестр нарушений;
- заявки сотрудников;
- запросы наказаний АБ;
- проверки АБ и архив проверок;
- отчёты;
- премирование;
- тесты;
- поставки;
- сообщения;
- документы;
- личный кабинет;
- информация, устав, услуги и медикаменты;
- состав, автопарк, FAQ и обучение;
- новости.

В текущей версии справочник ролей является страницей просмотра. Роли создаются на уровне данных/SQL, а назначаются пользователям через личный кабинет.

## 6. Настройка проекта через интерфейс сайта

### Личный кабинет — `lk.html`

Главная точка внутреннего администрирования:

- отображает данные текущего пользователя и его роль;
- показывает журнал действий по новостям, составу, заявлениям, жалобам, заявкам, нарушениям, проверкам, поставкам, премиям, тестам и ролям;
- фильтрует журнал по типу события и периоду;
- позволяет включать всплывающие уведомления и звук;
- позволяет выбрать конкретные категории уведомлений;
- управляет праздничным оформлением и текстом баннера;
- показывает список пользователей и назначенные роли;
- создаёт учётную запись и связывает её с выбранной ролью;
- изменяет отображаемое имя и роль;
- удаляет пользователя через защищённый серверный маршрут.

Пользовательские настройки оформления и звука сохраняются локально в браузере. Роли, праздничное состояние и общесайтовые настройки сохраняются в базе.

### Роли — `roles.html`

Страница выводит `custom_roles`, их ключ, базовую роль, цвет, описание и разрешённые действия. Она нужна для проверки фактического набора доступов. Назначение роли выполняется в `lk.html`.

### Формы заявок — `requests-settings.html`

Страница настраивает:

- минимальную должность для отгула и отпуска;
- максимальную продолжительность отгула и отпуска;
- начало и окончание рабочего распорядка;
- отдельное окончание смены в будни, выходные и праздники;
- обеденное время;
- время поверки и допустимое окно;
- правила учёта поставок в баллах для повышения;
- Discord-канал новой заявки и канал вердикта;
- до двух ролей для упоминания;
- список должностей для повышения;
- отделы, их каналы, роли и отдельные формы;
- поля формы для каждой должности: ключ, название, тип, подсказка, обязательность и варианты выбора.

Общие виды заявок используют `requests`, `request_forms` и `requests_settings`. Страницы `leave.html`, `vacation-ic.html`, `vacation-ooc.html`, `dismissal.html`, `promotion.html`, `restoration.html` и `appointment.html` используют общий `requests-engine.js`, но передают разный тип заявки.

### Электронные заявления — `apps.html`

Используются таблицы `applications` и `apps_settings`. Настройки определяют Discord-каналы, роли для упоминания и правила обработки. `apps-stats.html` строит статистику по пользователям, типам, статусам и периодам и может экспортировать результат в PNG.

### Жалобы и нарушения

- `complaints.html` — публичная подача жалобы;
- `complaints-form.html` — конструктор формы: заголовок, описание, группы и поля;
- `complaints-review.html` — рассмотрение, решение и создание записи нарушения;
- `complaints-settings.html` — каналы Discord, роль АБ, сроки действия и конвертация предупреждений;
- `complaints-stats.html` — сводная статистика жалоб и реестра.

Форма хранится в `complaint_form`. Жалобы — в `complaints`, история решений — в `complaint_history`. Действующие дисциплинарные записи находятся в `violations_registry`, а изменения — в `violations_history`.

В настройках задаются отдельные Discord-каналы для новых жалоб, вердиктов, приказов АБ, дисциплинарных заключений и снятия нарушений. Также задаются сроки предупреждения, выговора, беседы и заключения и количество предупреждений для автоматической конвертации в выговор.

### Проверки АБ — `vp.html`

Раздел использует:

- `vp_checks` — текущие проверки;
- `vp_archive` — завершённые записи;
- `vp_reports` и `vp_report_requests` — отчёты и запросы публикации;
- `vp_settings` — общие параметры;
- `vp_role_mapping` — соответствие Discord-ролей;
- `ds_sync_requests` — ручные запросы синхронизации.

`vp-request.html` формирует запрос наказания, а `vp-request-settings.html` настраивает типы запросов, иконки, цвет Embed, порядок, каналы публикации и вердикта, роли для упоминания и поля формы.

### Тестирование

- `tests.html` — список тестов, категории и результаты;
- `test.html` — прохождение выбранного теста;
- `test-editor.html` — создание и редактирование теста.

Редактор поддерживает:

- заголовок, slug, описание и вступительный текст;
- категорию;
- порог прохождения в процентах;
- показ правильных ответов;
- случайное перемешивание вопросов;
- ограничение количества вопросов за попытку;
- максимальное число попыток;
- таймер;
- Discord-канал результатов;
- блокировки по static ID или Discord;
- обычный выбор ответа;
- варианты с отдельными изображениями;
- вопросы «расставьте по порядку»;
- предзаполненные служебные поля.

Основные таблицы: `tests`, `test_categories`, `test_questions`, `test_attempts`, `test_blocks`, `test_ping_lines` и `test_result_requests`. Итог попытки создаётся RPC `submit_test_attempt`, после чего Discord-бот обрабатывает запрос результата.

### Состав — `composition.html`

Вся структура состава сохраняется как JSON-состояние в единственной записи `composition` с `id = 1`.

Редактор позволяет:

- создавать и переставлять подразделения;
- задавать полное и короткое название отдела;
- менять цвет, эмблему и число колонок по умолчанию;
- задавать своё количество карточек в каждой строке;
- создавать должности администрации и сотрудников отдела;
- назначать категорию должности;
- указывать ФИО, должность, static ID, спецсвязь и Discord ID;
- загружать фото и менять масштаб/позицию кадра;
- формировать ссылку `discord://-/users/ID`;
- экспортировать всю иерархию или отдельный отдел в PNG;
- включать или скрывать фото и контакты;
- выбирать масштаб PNG от 1× до 3×;
- экспортировать только карточки без общей обложки.

Фотографии текущей версии загружаются в Storage bucket `composition-photos`. В целевой PostgreSQL-версии они загружаются через API в каталог VPS.

### Новости — `news.html`

Новости находятся в таблице `news`. Редактор поддерживает:

- заголовок и дату;
- тег и отдел;
- главное изображение;
- дополнительные изображения;
- краткое описание для карточки;
- полный текст модального просмотра;
- создание, редактирование и удаление;
- локальные черновики через `draft-engine.js`.

`home-news.js` выводит последние публикации на главной. `news-reader.js` отвечает за полный просмотр записи.

### Контентные разделы

- `info.html` + `info-engine.js` — редактируемая информация о больнице, таблица `info_page`;
- `services.html` и `meds.html` + `site-data-engine.js` — услуги и медикаменты, таблица `site_data`;
- `ustav.html` + `ustav-engine.js` — главы устава, изображения и навигация, таблица `ustavy`;
- `learn.html` + `learn-engine.js` — учебные материалы по категориям, таблица `learn_materials`;
- `faq.html` + `faq-engine.js` — вопросы, категории и порядок, таблица `faq`;
- `autopark.html` + `autopark-engine.js` — карточки автомобилей в `vehicles` и фото в `autopark-photos`;
- `map.html` + `map-data.js` — статическая карта и локальное описание объектов;
- `docs.html` + `docs-editor.js` + `docs-templates.js` — конструктор официальных документов с динамическим количеством страниц, печатями и экспортом.

### Поставки

- `supply.html` — подача запроса;
- `supply-admin.html` — настройка полей формы;
- `supply-stats.html` — статистика;
- `supply-engine.js` — RPC и прикладная логика.

Используются `supply_form`, `supply_requests`, `supply_entries` и `supply_rescan_requests`. Форма загружается RPC `get_supply_form`, отправка выполняется `submit_supply_request`.

### Премирование

`payroll.html` использует `payroll_settings`, `payroll_drafts`, `payroll_archive` и `payroll_send_requests`. Черновик формируется функцией `ensure_payroll_draft`, архивируется `archive_payroll_draft`, а Discord-бот публикует подготовленный запрос отправки.

### Еженедельные отчёты

`report.html` строит форму из `report_forms`. `report-settings.html` настраивает тип отчёта, иконку, цвет, порядок, активность, Discord-канал, роли для упоминания и произвольный список полей. Созданные запросы публикации находятся в `report_send_requests`.

## 7. Уведомления и журнал событий

### Уведомления внутри сайта

`notify-engine.js` и `notify-live.js` активируются только для авторизованного пользователя. Они читают последние записи доступных роли разделов, хранят список уже просмотренных идентификаторов и показывают новые события во всплывающей панели.

Настройки пользователя находятся в личном кабинете:

- общий переключатель уведомлений;
- звук;
- выбор типов событий;
- фильтрация по роли и разрешениям.

### Журнал в личном кабинете

`audit-feed.js` объединяет события из разных таблиц в одну ленту. Поддерживаются новости, автопарк, устав, уроки, тесты, праздничное оформление, состав, налёты, заявления, жалобы, заявки, нарушения, проверки, поставки, премии и изменения ролей.

Журнал строится из фактических записей разделов, а не из отдельной универсальной таблицы аудита. Имена Discord-пользователей дополняются данными `ds_members`.

## 8. Discord-бот

Discord-бот является отдельным Node.js-процессом. Его основная точка запуска — `index.js`.

### Модули Discord-бота

- `index.js` — запуск клиента, основная маршрутизация и электронные заявления;
- `postgres-client.js` — совместимый клиент PostgreSQL и подписка `LISTEN cgb_changes`;
- `parser.js` — разбор сообщений Discord и данных сотрудников;
- `vp.js` — проверки АБ и синхронизация;
- `vp-report.js` — публикация отчётов проверок;
- `vp-request.js` — запросы наказаний и вердикты;
- `test-report.js` — результаты тестов;
- `supply.js` — поставки и связанные запросы;
- `complaints.js` — жалобы, нарушения и сроки;
- `payroll.js` — премирование;
- `requests.js` — отгулы, отпуска, увольнения, повышения, восстановления и запись;
- `report.js` — еженедельные отчёты;
- `raids.js` — события налётов;
- `msg.js` — служебные сообщения с сайта;
- `reactions.js` — обработка реакций бота.

### Запуск и синхронизация

После входа бот:

1. записывает состояние в `bot_status`;
2. читает конфигурацию заявлений;
3. синхронизирует Discord-каналы в `ds_channels`;
4. синхронизирует роли в `ds_guild_roles`;
5. синхронизирует участников и разобранные никнеймы в `ds_members`;
6. запускает подписку на события базы;
7. запускает обработчики очередей отдельных модулей;
8. периодически перечитывает настройки, чтобы изменения на сайте применялись без перезапуска.

В подготовленной PostgreSQL-версии совместимый интерфейс `.channel().on().subscribe()` реализован поверх PostgreSQL `LISTEN/NOTIFY`. Событие содержит таблицу, операцию и идентификатор строки; полный объект бот получает отдельным запросом.

### Настройки Discord из сайта

Списки каналов и ролей в настройках сайта берутся не из вручную введённого текста, а из `ds_channels` и `ds_guild_roles`. Поэтому после добавления канала или роли на Discord-сервере бот должен выполнить очередную синхронизацию, после чего значение появляется в выпадающих списках сайта.

Для каждого прикладного раздела могут задаваться:

- канал публикации новой записи;
- отдельный канал вердикта;
- одна или две роли для упоминания;
- цвет и заголовок Embed;
- активность формы;
- набор полей формы.

## 9. Telegram-бот

Telegram-часть состоит из фонового Python-воркера и страницы `telegram-settings.html`.

### Таблицы

- `telegram_settings` — главный переключатель и маршруты;
- `telegram_topics` — зарегистрированные группы и темы;
- `telegram_notifications` — очередь и история отправки;
- `telegram_bot_status` — состояние процесса и время последнего heartbeat.

### Регистрация тем

Бот добавляется в частную группу с включёнными темами. Внутри каждой темы выполняется:

```text
/register Название темы
```

Дополнительные команды:

- `/status` — состояние бота;
- `/chatid` — идентификаторы группы и текущей темы.

После регистрации тема появляется на `telegram-settings.html`. Администратор связывает её с одним из маршрутов и сохраняет настройку.

### Маршруты

- экзамены и вердикты;
- повышения;
- электронные заявления и восстановления;
- увольнения;
- отпуска IC и OOC;
- отгулы.

При появлении события создаётся запись `telegram_notifications`. Воркер получает ожидающие записи, формирует текст и вызывает Telegram Bot API. После отправки сохраняются статус и ID Telegram-сообщения. При ошибке сохраняется описание и запись может быть обработана повторно.

Страница настроек показывает состояние процесса, число зарегистрированных тем, размер очереди, последние отправки и позволяет отправить тестовое уведомление по каждому маршруту.

## 11. RPC-функции приложения

Рабочий интерфейс вызывает 12 функций базы:

- `staff_upsert_role` — назначение роли пользователю;
- `get_complaint_form` — получение формы жалобы;
- `submit_complaint` — создание жалобы;
- `submit_request` — создание общей заявки;
- `get_supply_form` — получение формы поставок;
- `submit_supply_request` — отправка поставки;
- `count_test_attempts` — количество попыток;
- `check_test_blocked` — проверка блокировки;
- `submit_test_attempt` — фиксация прохождения;

- `ensure_payroll_draft` — получение или создание черновика премии;
- `archive_payroll_draft` — архивирование премирования.

RPC используются там, где одной операции над таблицей недостаточно: необходимо проверить ограничения, атомарно изменить несколько записей или разрешить публичную отправку только через контролируемую функцию.

## 12. Realtime и фоновые обновления

Текущий клиент использует Supabase Realtime для каналов `cr-live` и `vp-live` и периодическое обновление для остальных разделов. Уведомления сайта не опрашиваются, когда вкладка скрыта, чтобы не выполнять лишние запросы.

Discord-бот сочетает событийные подписки и интервальные обработчики. Это связано с тем, что часть очередей должна повторно подхватываться после временного отключения бота.

В целевой базе PostgreSQL триггеры публикуют компактные события в канал `cgb_changes`. Discord-клиент подписывается через `LISTEN cgb_changes`, а затем перечитывает изменённую запись. Telegram использует очередь со статусами и короткий интервал опроса, поскольку для отправки важны повторные попытки и фиксация результата.

## 13. Хранение изображений и экспорт

### Текущая версия

- bucket `composition-photos` — фотографии состава;
- bucket `autopark-photos` — изображения автопарка;
- локальные `assets/`, `images/` и `uploads/` — статические изображения сайта;
- URL фотографий сохраняется внутри записи раздела.

Перед загрузкой выполняется клиентская подготовка изображения через `image-compress.js`. Для состава дополнительно сохраняются масштаб и позиция кадра, поэтому один оригинал можно отображать в карточке с выбранным кадрированием.

### PostgreSQL-версия

API принимает изображения в маршруте `/api/v1/storage/:bucket/*object`, сохраняет их в `/var/lib/cgb-storage` и возвращает публичный адрес `/media/...`. В базе хранится только путь и метаданные; бинарное содержимое в PostgreSQL не помещается.

### PNG

`html2canvas.min.js` и `png-export-utils.js` создают изображение непосредственно в браузере. Сервер и база в генерации PNG не участвуют. Этот механизм используется составом, статистикой и медицинскими услугами.

## 14. Подготовленный API автономной версии

Собственный Node.js API слушает `127.0.0.1:8787`, а Nginx публикует его под `/api/v1`.

Маршруты:

- `GET /api/v1/health` — состояние API и базы;
- `POST /api/v1/auth/login` — вход;
- `POST /api/v1/auth/refresh` — обновление сессии;
- `POST /api/v1/auth/logout` — завершение сессии;
- `GET /api/v1/auth/session` — текущий пользователь;
- `PATCH /api/v1/auth/user` — изменение профиля;
- `GET /api/v1/auth/admin/users` — список пользователей;
- `POST /api/v1/auth/admin/users` — создание пользователя;
- `DELETE /api/v1/auth/admin/users/:id` — удаление пользователя;
- `POST /api/v1/db/query` — разрешённые запросы к таблицам;
- `POST /api/v1/db/rpc/:name` — вызов разрешённой функции;
- `PUT /api/v1/storage/:bucket/*object` — загрузка изображения;
- `DELETE /api/v1/storage/:bucket` — удаление объекта.

`database-client.js` повторяет используемую сайтом цепочку запросов Supabase (`from`, `select`, `eq`, `order`, `limit`, `insert`, `update`, `delete`, `upsert`, `rpc`). Благодаря этому страницы переводятся на API без полной переработки каждого раздела.

Авторизация PostgreSQL-версии использует таблицы пользователей, bcrypt-хеш пароля, короткий access JWT и обновляемый refresh token. Удаление пользователя каскадно удаляет его роли и refresh-сессии.

## 17. Техническая связь между разделами

Основные цепочки данных:

```text
Форма на сайте
  → таблица или RPC
  → запись заявки
  → триггер/очередь
  → Discord-бот и/или Telegram-воркер
  → сообщение в выбранный канал/тему
  → решение сотрудника
  → статус и история в БД
  → обновлённая карточка на сайте
```

```text
Discord-сервер
  → бот читает каналы, роли и участников
  → ds_channels / ds_guild_roles / ds_members
  → выпадающие списки настроек сайта
  → выбранные ID сохраняются в настройках раздела
  → бот использует их при следующем событии
```

```text
Администратор сайта
  → создаёт пользователя
  → назначает custom_role
  → roles-engine загружает permissions
  → data-perm скрывает или открывает элементы
  → политика БД/API проверяет операцию на серверной стороне
```

Таким образом, интерфейс сайта отвечает за ввод и настройку, база — за состояние и очереди, а боты — за интеграцию с Discord и Telegram.
